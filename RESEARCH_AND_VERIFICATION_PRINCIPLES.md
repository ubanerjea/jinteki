# Vetting research, and writing verification for builds

Companion to `AGENTS.md`'s "Workflow: research → vet → build → verify" section. This doc is the two skills that section leaves to human/orchestrating-session judgment: deciding a research pass is actually solid enough to build from, and deciding what "verified" concretely means for a given build. Both are grounded here in jinteki's actual shape — a small, well-bounded card-game dataset (thousands of cards/formats, tens of thousands of decklists, not millions of anything), plain Postgres/Prisma with no dedicated search engine, no UI component library, and no headless browser available in this environment.

## Vetting research

- **Trust the report's own source-tagging, then spot-check the load-bearing claims.** A good research pass in this project already marks each claim as directly fetched, sourced only via a secondary/fallback path, or general/unconfirmed. Vetting isn't re-deriving everything yourself — it's picking the handful of claims the recommendations most depend on and confirming those directly (one real request, one query, one version check), and treating anything tagged unconfirmed as context, never as a build input on its own.
- **A recommendation is only as good as its anchors.** Before accepting one, confirm the table, column, endpoint, or file it names actually exists as described — not "plausible," verified. Research about an external system especially needs this: an API shape or UI pattern described from memory or a blocked/mirrored source can be subtly wrong in exactly the way that matters.
- **Require an implementation sketch, not just a direction.** "Add a way to filter by X" isn't vetted yet; "add a nullable column here, filtered via this query shape, because the real API confirmed no such field already exists" is. If a build agent would need to re-research to act on a recommendation, send it back for another pass rather than accepting it as scope.
- **Actively prune deliberate non-goals, don't just approve gaps.** A research pass surfaces both real gaps and things this project has already decided against (e.g. features that assume infrastructure or a product shape jinteki doesn't have). Vetting means removing the latter from scope, not letting everything through because it was mentioned.
- **Recognize this project's recurring idioms when a recommendation fits one.** Small, rarely-changing reference data (a handful of rows, changes maybe once a year) is a hand-curated seed file reviewed as a code diff, not a scraper or a DB-editable admin table — jinteki already has this pattern twice. A recommendation that reinvents infrastructure for a problem this project has already solved a certain way should be redirected to the existing idiom, not built fresh.

## Writing verification for a build

- **Every check needs a computed expected value, not a vibe.** Not "the filter should work" but "77 rows, per this exact query" — ideally computed before the build exists, so the expected number isn't itself derived from the code under test.
- **Verification must be independently derivable, never a re-read of the build's own code or report.** Re-run the underlying query yourself; boot the server fresh; don't accept "I checked, it's fine" as evidence. A build's own self-verification can be wrong in ways that look like confirmation — this project has had a self-reported "pre-existing, unrelated" diagnosis that turned out to be caused by the very change being verified, because the check used to rule it out (reverting file changes) couldn't actually undo the real cause (an already-applied database migration).
- **Bake in this project's standing hazards as unconditional checks, on top of whatever's feature-specific.** Any schema-touching change should reconfirm nothing unrelated got dropped — this project's Postgres GIN indexes are invisible to Prisma's own schema file, so a routine auto-generated migration once silently deleted five of them for real, and that class of check now belongs in every schema-adjacent verification, not just the one that found it.
- **Dev mode passing is not sufficient for anything route- or auth-related.** A separate, from-scratch production build+start check is mandatory whenever a build touches routes or auth-gating — this project has a confirmed case where a production-only bug (an env-driven auth setting defaulting differently under `next start` than `next dev`) was invisible in dev mode and only surfaced once someone actually ran the production build.
- **Use real HTTP requests as the browser stand-in, and name what that can't cover.** No headless browser exists in this environment, so verification leans on curl and rendered-HTML inspection for everything checkable that way — and should say plainly, not gloss over, that visual/interactive behavior (layout, mouse interactions) still needs a human to actually look at it.
- **Match verification depth to the data's real scale.** jinteki's tables are small; the risk here is a wrong row, not a slow query. Spend verification effort on exactness (precise counts, set equality between what a page renders and what the database actually has) rather than performance/load testing, which isn't this project's risk profile.
