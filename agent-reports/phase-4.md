# Phase 4 — Card & Decklist Browsing + Search: Task Report

Scope built per `plans/PHASE_4_PLAN.md` (informed by `plans/PROJECT_PLAN.md`): a real homepage, `/cards` + `/cards/[code]`, `/decklists` + `/decklists/[id]`, a shared `src/lib/search/` query layer wrapping the `pg_trgm` trigram queries as typed, tested functions, and Vitest tests for the search logic. Rules-glossary browsing, the right-click rulings/rules menu, and favorites remain out of scope per the plan's "Explicitly deferred" list and were not touched. No schema changes were needed this phase - confirmed via `npx prisma migrate status` ("Database schema is up to date!") and `git status` showing `prisma/schema.prisma` untouched.

## What was built

### 1. Investigation before writing any query/UI code (per the plan's explicit instructions)

- **`Card.raw` printing/image shape**, inspected directly via `psql` against real synced rows (not assumed from memory): NRDB v3's `cards` resource already ships a ready-made hotlink URL per size at `attributes.latest_printing_images.nrdb_classic.{tiny,small,medium,large,xlarge}`, confirmed **non-null on all 2054 currently-synced cards** (`SELECT count(*) FROM "Card" WHERE raw->'attributes'->'latest_printing_images'->'nrdb_classic' IS NULL` → `0`). This is better than the "pick an entry out of `printing_ids`" heuristic the plan anticipated, so `src/lib/card-image.ts` uses that field directly rather than reconstructing a URL. For the record, also confirmed (on `sure_gamble`): `printing_ids` is newest-first (`printing_ids[0]` === `latest_printing_id`) and `card_set_ids`'s *last* entry is the original release pack - consistent with `sync-cards.ts`'s existing `packCode` heuristic from Phase 2.
- **`pg_trgm` default threshold behavior on real data**: ran real `similarity()`/`%` queries against the live 2054 cards / ~74k decklists before writing any query code (see the "Verification" section below for the actual output). The default 0.3 threshold gave sensible results on both a short card title ("Sure Gamble" exact match: similarity 1; typo "Sur Gambl": 0.57, still matched) and a longer decklist name ("NBN Rush" typo "NBN Rsh": still returned "NBN Rush" and other Rush decks). No threshold override was needed.
- **`Faction.description` is not a usable short label**: confirmed via `psql` that it holds a full flavor-text paragraph for named factions (Anarch, Criminal, ...) and only falls back to a short name for mini-factions/neutrals (per `sync-factions-packs.ts`'s existing `mapFaction` fallback logic from Phase 2). There's no separate short-name column. Faction/type/side display labels are instead derived from their `code` via `src/lib/format.ts`'s `formatCode()` (e.g. `haas_bioroid` → "Haas Bioroid"), not from `description`.
- **No per-printing illustrator/flavor-text-per-printing data exists**: the plan mentioned "pack/illustrator" as possible detail-page fields. NRDB v3's abstracted `cards` resource (which is all that's synced - there's no `Printing` model in this schema) has no illustrator field; flavor text does exist at the card level as `narrative_text` (confirmed non-null on several identity/bio cards, e.g. `au_co_the_gold_standard_in_clones`). The detail page shows pack (via the existing `Card.pack` relation) and `narrative_text`; illustrator is not shown since the data was never synced (not a Phase 4 regression - a Phase 2 schema/scope decision).
- **`vitest` does not auto-load `.env`**, unlike `tsx` (which the `pnpm sync:*` scripts run under and does load it) - confirmed by a throwaway test that printed `process.env.DATABASE_URL` under each runner. This mattered because Phase 4 is the first phase with tests that need a real DB connection (searchCards/searchDecklists integration tests). Fixed in `vitest.config.ts` with a small hand-rolled `.env` parser (no new dependency - the file's format is simple `KEY=VALUE` lines) feeding `test.env`.

### 2. Search query layer — `src/lib/search/`

- **`types.ts`** — `PagedResult<T>`, `SearchParamsInput` (Next's `searchParams` shape: `Record<string, string | string[] | undefined>`), `firstParam()` helper (takes the first value when a query param is repeated in a URL).
- **`pagination.ts`** — pure functions with no DB access: `parsePage`, `parsePageSize` (clamped to `[1, MAX_PAGE_SIZE=100]`, default page size 30), `pageOffset`, `toPagedResult` (reports `totalPages: 1`, not `0`, for an empty result set, so callers never need a special case). Fully unit-testable without Postgres.
- **`cards.ts`** — `parseCardSearchParams(searchParams)` + `searchCards(params)`. Structured filters (`faction`/`side`/`type`) are plain `Prisma.sql` equality fragments; free-text `q` matches `title % q OR text % q` (trigram), ranked by `GREATEST(similarity(title,q), similarity(coalesce(text,''),q))` when a query is present, alphabetical by title otherwise (an explicit stable order matters for pagination correctness - see Phase 2's decklist-pagination bug in `agent-reports/phase-2.md` for why an *unordered* full list is a real bug, not just a nicety).
- **`decklists.ts`** — `parseDecklistSearchParams(searchParams)` + `searchDecklists(params)`. `identity` filter is an exact `identityCode` match; `q` is trigram search on `Decklist.name`. Joins `Card` for the identity's title so the list page doesn't need N+1 queries.
- Every conditional fragment (`Prisma.sql` calls) and the final query are composed via `Prisma.sql`/`Prisma.join`/`Prisma.empty` tagged templates - see the "no raw-SQL injection risk" section below.

### 3. Pages (all Server Components, `searchParams`/`params` as `Promise<...>` per this Next.js version's async-prop convention, already established by `src/app/api/admin/sync/[type]/route.ts`)

- **`src/app/page.tsx`** — replaced the default `create-next-app` scaffold with minimal nav to `/cards` and `/decklists`. `src/app/layout.tsx`'s `metadata` (title/description) updated away from "Create Next App" branding too.
- **`src/app/cards/page.tsx`** — plain `<form method="get">` (no client JS/component needed - a GET form navigates with a query string on its own) with `q`/`faction`/`side`/`type` inputs, a result count, a list linking each card to its detail page, and `PaginationNav`. Faction options come from `prisma.faction.findMany()`; type options from `prisma.card.groupBy({ by: ["typeCode"] })`; side options are the two known values (`corp`/`runner`, confirmed via `psql` as the only two `sideCode` values in the table).
- **`src/app/cards/[code]/page.tsx`** — detail page: image (via `getCardImageUrl`), faction/type/side, subtypes (`keywords`), a generic "whichever of these fields are present" attribute renderer (cost, strength, advancement requirement, agenda points, trash cost, influence, MU, base link, minimum deck size, influence limit - looked up in `raw.attributes` and only rendered when non-null, so it adapts to whatever fields a given card type actually has rather than branching per `typeCode`), full card text, flavor text (`narrative_text`), and pack name. `notFound()` (real Next.js 404) for an unknown code.
- **`src/app/decklists/page.tsx`** — `q` + `identity` filter (dropdown of the 148 identities actually used by at least one decklist, via the existing `Card.decklistsAsIdentity` relation - not all ~2000 cards), result count, list linking each decklist to its detail page and its identity to the card detail page, `PaginationNav`.
- **`src/app/decklists/[id]/page.tsx`** — detail page: name, identity (linked to `/cards/[code]`), full card list with quantities (sorted by type then title), each card linked to its own detail page. `notFound()` for an unknown id.
- **`src/components/pagination-nav.tsx`** — shared server-rendered Previous/Next component, preserves every other current search param when linking to an adjacent page.
- **`src/lib/format.ts`** — `formatCode()` (code → title-case label, with an `nbn` → "NBN" override).
- **`src/lib/card-image.ts`** — `getCardImageUrl(raw, size)`, documented above.

Images are rendered with a plain `<img>` (one `eslint-disable-next-line @next/next/no-img-element` with an inline comment explaining why), not `next/image` - deliberately, since `next/image`'s optimization pipeline would fetch/re-encode hotlinked images through this app's own server, which conflicts with `PROJECT_PLAN.md`'s explicit "hotlinked directly... no local caching of images" decision.

### 4. Tests — `src/lib/search/*.test.ts` (38 new tests, on top of the existing 27)

- **`pagination.test.ts`** (pure, no DB): `parsePage`/`parsePageSize` edge cases (missing, fractional, zero, negative, non-numeric garbage, absurdly-large-clamped-to-`MAX_PAGE_SIZE`), `pageOffset`, and `toPagedResult`'s ceiling-division/empty-result/exact-remainder behavior.
- **`cards.test.ts`** / **`decklists.test.ts`** (integration, real DB - per the plan's own note that trigram-ranking behavior needs a real Postgres connection, unlike Phase 2/3's fixture-based mapper tests): `parseCardSearchParams`/`parseDecklistSearchParams` param-parsing behavior; `searchCards`/`searchDecklists` against the real, already-synced data - empty query lists results (doesn't error/return nothing), exact-name search finds the exact card/decklist, a typo'd search still returns something reasonable, structured filters' `total` matches a direct `prisma.count()` with the same `WHERE`, pagination has no overlap between adjacent pages and the last page has the exact remainder, and (decklists only) an automated `EXPLAIN` test asserting the query plan contains `Decklist_name_trgm_idx` and not `Seq Scan on "Decklist"` - this encodes the plan's index-usage requirement as a real regression test, not just a one-off manual check.

## Hard requirement: no raw-SQL injection risk — verified

`grep -rn '\$queryRawUnsafe\|executeRawUnsafe' src` returns **zero real usages** - the only hit is a comment in `cards.ts` explaining why it's *not* used. Every `$queryRaw` call in the app (`cards.ts:104,111`, `decklists.ts:72,80`) is built exclusively from `Prisma.sql`/`Prisma.join`/`Prisma.empty` tagged-template fragments, including every fragment that carries user-controlled input (`q`, `faction`, `side`, `type`, `identity`) - Prisma auto-parameterizes every `${...}` interpolation inside a `Prisma.sql` template, so no user input ever reaches the query as concatenated/interpolated raw text. (The one other `$queryRaw` call, in `decklists.test.ts`'s `EXPLAIN` regression test, uses a hardcoded literal string in test code, not user input, and is itself Prisma's safe tagged-template form.)

## Deviations from the plan, summarized

1. **Card image URL taken directly from `raw.attributes.latest_printing_images.nrdb_classic`** rather than deriving one from `printing_ids`/`card_set_ids` as the plan anticipated might be necessary - a strictly better outcome discovered by doing the plan's own "inspect real rows first" instruction, not a shortcut. The `printing_ids`-based heuristic is kept as a documented, unused-in-practice defensive fallback in `getCardImageUrl()` in case a future sync ever hits a card missing that field.
2. **Faction/type/side display labels derived from `code` (`formatCode()`)** rather than from `Faction.description`, since `description` is flavor text for named factions (not a short label) - a display-only decision, not a data/schema change.
3. **`vitest.config.ts` gained a small hand-rolled `.env` parser** (`test.env`) - necessary because this is the first phase with tests needing a real `DATABASE_URL`, and Vitest (unlike the `tsx`-run sync scripts) doesn't load `.env` on its own. No new dependency added for this - the repo's `.env` format is simple enough for a ~20-line parser.
4. **Illustrator field not shown on the card detail page** despite being mentioned in the plan's field list - not available in the synced data (NRDB v3's abstracted `cards` resource has no illustrator field at the card level; that's a per-printing concept and there's no `Printing` model in this schema). Documented in code and here rather than silently omitted.
5. **`BigInt(0)` instead of `0n`** in both search modules' count-query fallback - a real `tsc` error under this project's `ES2017` target, not a style choice.

No scope reduction: every page/route/module named in `PHASE_4_PLAN.md`'s "Card browsing" / "Decklist browsing" / "Search query layer" / "Testing" sections was built, and the "Explicitly deferred" list (rules-glossary UI, right-click menu, favorites, admin UI polish) was left untouched.

## Left unresolved / requires the repo owner's manual action

1. **The card-search sequential-scan finding** (row 8 of the Verification table above) is not a defect but is worth the owner's awareness: `/cards?q=...` does a full table scan rather than using the trigram indexes, because it searches `title OR text` rather than a single column. At 2054 rows this is fast (~25ms) and not worth optimizing yet; if the card catalog ever grows by an order of magnitude, revisit (e.g. a `UNION` of two single-column indexed queries, or a combined `tsvector`/expression index).
2. **No illustrator data** is shown on card detail pages, since it was never synced (a Phase 2 schema/scope boundary, not something this phase could add without a new sync + schema change, which is out of scope here).
3. Nothing from `PHASE_4_PLAN.md`'s "Explicitly deferred" list was started: no rules-glossary browsing/search UI, no right-click rulings/rules menu, no favorites UI, no admin UI polish.

Working tree was **not** committed or pushed, per instructions. `git status` at the end of this session shows `src/app/layout.tsx`, `src/app/page.tsx`, `vitest.config.ts` modified, plus `src/app/cards/`, `src/app/decklists/`, `src/components/`, `src/lib/card-image.ts`, `src/lib/format.ts`, `src/lib/search/` as new/untracked - ready for the owner's review.
