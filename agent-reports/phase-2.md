# Phase 2 — NRDB Data Sync: Task Report

Scope built per `plans/PHASE_2_PLAN.md` (informed by `plans/PROJECT_PLAN.md`): an NRDB API client, four dependency-ordered sync scripts (factions+packs → cards → decklists → rulings) with a `SyncRun` log table, an admin-gated trigger surface (API route + minimal page), and Vitest tests for every mapping function. The rules-doc scraper, all browsing/search UI, and favorites UI remain out of scope per the plan's "Explicitly deferred" list and were not touched.

## What was built

### 1. NRDB API research (no endpoints assumed from memory)

Confirmed live against `https://api.netrunnerdb.com/api/docs` and by hitting real endpoints directly:

- **Base URL**: `https://api.netrunnerdb.com/api/v3/public` (JSON:API format). Note: the docs page's own example requests point at `api-preview.netrunnerdb.com`, which returned HTTP 503 from this machine every time it was tried; `api.netrunnerdb.com` — the host actually linked from every resource's `links.self` in real responses — is what's live and what the client uses.
- **Pagination**: `page[number]` / `page[size]`, `links.next` present iff another page exists, `meta.stats.total.count` gives the live total. No documented hard cap on `page[size]` was found (`page[size]=5000` on `/cards` returned all 2054 rows in one page).
- **Resource shapes**: `/factions` (12 rows: 8 named + `neutral_corp`/`neutral_runner`), `/card_sets` (= our `Pack`, 75 rows) vs `/card_cycles` (groupings of card_sets, not stored — nothing in the schema needs them), `/cards` (2054 rows, one per unique card **across all reprints**, not one per printing — `card_set_ids`/`printing_ids` list every set/printing it's ever appeared in), `/decklists` (74233 rows), `/rulings` (886 rows).
- **`filter[updated_at][gte]=<ISO date>` verified to genuinely filter server-side**: a far-future cutoff (`2099-01-01`) reliably returns `meta.stats.total.count: 0`, ruling out "the param is silently ignored." This is what makes incremental decklist sync possible.
- **`sort=created_at,id` verified accepted** (compound sort, HTTP 200) — this became load-bearing after a bug found during verification (see below).

### 2. `src/lib/nrdb/client.ts` + `src/lib/nrdb/types.ts`

Thin typed fetch wrapper: `paginate()` (async generator, sequential page fetches with a 250ms default delay — no parallel hammering of NRDB, per the plan), `fetchAll()` (buffers small collections), `NrdbApiError`. `types.ts` has loosely-typed JSON:API resource interfaces for factions, card_sets, cards, decklists, rulings — only the fields the mappers actually read are typed strictly, everything else falls through `[key: string]: unknown` since the full API object is preserved verbatim in `Card.raw` / `Decklist.raw`.

### 3. Schema change — `prisma/migrations/20260728000126_add_sync_run_and_ruling_nrdb_id/`

Added the `SyncRun` model exactly as specified in `PHASE_2_PLAN.md` (`SyncType`/`SyncStatus` enums, `id`/`type`/`status`/`startedAt`/`finishedAt`/`recordCount`/`errorMessage`).

**Deviation beyond the plan's stated schema change**: also added `Ruling.nrdbId Int @unique`. The original `Ruling` model (from Phase 1) has no natural key besides an autoincrement `id` — there was no column to upsert against, which is a hard requirement for "idempotent, safe to re-run" sync scripts. `nrdbId` stores NRDB's own numeric ruling id and is the actual upsert key `sync-rulings.ts` uses. Justified as necessary to satisfy the plan's own idempotency requirement, not scope creep.

**Migration mechanics note**: `prisma migrate dev` could not be run at all in this non-interactive shell — Prisma detects the non-TTY environment and refuses even with `--create-only` (a change from whatever behavior Phase 1 saw; possibly because this migration's `ADD COLUMN ... NOT NULL` triggered an extra confirmation warning Prisma insists on prompting for). Worked around with `prisma migrate diff --to-schema-datamodel` to generate the raw SQL, hand-trimmed, then applied via `prisma migrate deploy` (CI-safe, no prompts). The raw diff output also proposed **dropping all five Phase-1 `pg_trgm` GIN indexes** (they aren't expressed via Prisma's schema syntax, so the diff tool sees them as drift) — that block was deliberately excluded from the final migration file; verified via `\di *trgm*` that all five survived.

Also hit a stale advisory-lock timeout (`P1002`) on the first migration attempt — an orphaned Postgres backend from an earlier, unrelated session had been idle for ~1h40m mid-`DROP DATABASE prisma_migrate_shadow_db...`. Resolved with `pg_terminate_backend()`; not caused by this session's own work.

### 4. Sync modules — `src/sync/`

- `sync-run.ts` — `SyncRun` bookkeeping (`startSyncRun`, `finishSyncRunSuccess/Failure`, `withSyncRun` wrapper, `getLatestSuccessfulRun`, `getLatestRun`), shared by every sync module *and* the admin API route so a CLI-triggered run and a browser-triggered run produce identical log rows.
- `sync-factions-packs.ts` — `mapFaction` (falls back to `name` when NRDB's `description` is null/empty, which is true for mini-factions and neutrals — the Phase 1 schema only has one `description` column, no separate `name`), `mapPack`, `runFactionsPacksSync`.
- `sync-cards.ts` — `mapCard`. Notable mapping decision: since NRDB v3's `cards` resource is de-duplicated across reprints (`card_set_ids` lists every pack a card was ever printed in, newest-first) but our schema models one `packCode` per card, `packCode` is taken as the **last** entry in `card_set_ids` (the original release) — verified against two real multi-printing cards (Sure Gamble, Diesel) where the array's last entry is `core_set`, matching the card's own `date_release`. Documented in code as a heuristic, not a documented API guarantee.
- `sync-decklists.ts` — `mapDecklist`, `mapDecklistCards`, `runDecklistsSync`. See "Bug found and fixed during verification" below — this file went through a real debugging cycle, not just a first-pass implementation.
- `sync-rulings.ts` — `mapRuling`, `runRulingsSync`. Full resync every time (886 rows is cheap); upserts on `nrdbId`.
- `sync-all.ts` — CLI-only, runs all four in order, aborts on first non-`SUCCESS`.

**Structural decision**: each of the four sync files contains its mapper function(s), its `run*Sync()` function, and a CLI-guard (`isDirectRun` check via `import.meta.url` vs `process.argv[1]`) all in one file, rather than splitting logic/CLI into separate files. This keeps exactly the four filenames the plan named while letting Vitest import the pure mapper functions without triggering a live network call (the CLI guard body never executes on import), and letting the admin API route / `sync-all.ts` import the same `run*Sync` functions the CLI scripts use.

**`package.json` scripts added**: `sync:factions`, `sync:cards`, `sync:decklists`, `sync:rulings`, `sync:all` (all via `tsx`), `test` (`vitest run`).

### 5. Bug found and fixed during verification (decklists pagination)

This is the most significant finding from this phase and is worth its own section.

The plan's Verification section calls for checking real row counts via `psql` — doing that caught a genuine bug rather than a rubber-stamp pass. The first full `pnpm sync:decklists` run (no `sort` param, ~14 minutes wall clock) reported `[sync:decklists] SUCCESS - 74233 records` — matching NRDB's live total exactly — but `SELECT count(*) FROM "Decklist"` showed only **47,814** distinct rows. `/decklists` has no deterministic default order; over a 14-minute, ~370-page crawl against a live, constantly-mutating production table, offset-based pagination without an explicit stable sort meant some decklists were fetched on multiple pages (in the worst case, processed *concurrently* by two different local batches, racing their `deleteMany`+`createMany` DecklistCard writes against each other) while others were skipped entirely — netting a large permanent shortfall despite the `recordCount` metric looking clean.

Diagnosis: fetched `/decklists?page[number]=1&page[size]=5` twice back-to-back (identical, ruling out "just no ordering at all"), then tested `sort=created_at` and the compound `sort=created_at,id` live (both HTTP 200, deterministic ascending order from NRDB's earliest 2013 decklist). Fix applied in `sync-decklists.ts`:
- Always pass `sort=created_at,id` — immutable per row, so paging forward is safe against concurrent inserts/updates on NRDB's side (new decklists only ever land past the current page; already-visited rows can't reappear later since their sort key can't change).
- Changed the return value of the per-page sync helper from a count to the actual list of successfully-synced ids, deduplicated into a `Set` across the whole run — belt-and-braces on top of the sort fix, so `recordCount` reflects truly distinct rows even if pagination is ever imperfect again.
- Before re-running: `TRUNCATE "DecklistFavorite", "DecklistCard", "Decklist"` and deleted the bad `DECKLISTS` `SyncRun` row (its `startedAt` would otherwise have become a misleading "incremental baseline," permanently hiding the ~26k-row historical gap from every future incremental run).

Re-run with the fix: `[sync:decklists] SUCCESS - 74233 records`, and this time `SELECT count(*) FROM "Decklist"` also shows **74233** — record count and actual row count now agree exactly. Cross-checked one decklist's `raw` JSON `card_slots` keys 1:1 against its `DecklistCard` rows (22/22 match, quantities included), and confirmed `avg(sum(quantity) per decklist) = 49.7` exactly matches `avg(NRDB's own num_cards + 1 for identity) = 49.7` across all 74233 decklists.

### 6. Admin trigger surface

- `POST /api/admin/sync/[type]` (`src/app/api/admin/sync/[type]/route.ts`) — `requireAdmin()` gate (401 if not authenticated, 403 if authenticated but not admin — distinguished by parsing `requireAdmin()`'s thrown message), maps the URL's kebab-case `type` (`factions-packs`/`cards`/`decklists`/`rulings`) to the matching `run*Sync` function, returns `{ run: SyncRun }` (200 on success, 500 with `{ error }` on failure — `run*Sync` already recorded the `SyncRun` as `FAILED` before rethrowing, so this just turns that into a proper HTTP response instead of a crash page). Unknown `type` → 400.
- `/admin/sync` (`src/app/admin/sync/page.tsx` + `src/app/admin/sync/sync-trigger-button.tsx`) — server component gated by the same `requireAdmin()` (renders "Access denied: <message>" instead of the table on failure), lists all four sync types with their most recent `SyncRun` (status/started/finished/record count/error), and a client "Trigger" button per row that `POST`s to the API route then `router.refresh()`s. Deliberately unstyled per the plan's "functional only" instruction.

## Deviations from the plan, summarized

1. **`Ruling.nrdbId` added** beyond the plan's stated `SyncRun`-only schema change — required for idempotent upserts (see above).
2. **Migration applied via `migrate diff` + `migrate deploy`** instead of `migrate dev`, because this non-interactive shell couldn't get past `migrate dev`'s confirmation prompt even with `--create-only`. Hand-trimmed the diff to preserve Phase 1's `pg_trgm` indexes, which the diff tool wanted to drop.
3. **`sort=created_at,id` added to the decklist sync**, not mentioned in the plan — a genuine, unplanned discovery made necessary by the bug above. Without it, decklist sync silently loses ~35% of rows while still reporting a "successful" count that matches NRDB's total.
4. **Local write concurrency (`LOCAL_WRITE_CONCURRENCY = 20`) added to decklist sync** for throughput — a single-decklist-at-a-time approach would have taken hours for ~74k rows. NRDB itself is still fetched strictly sequentially, one page at a time (never in parallel) per the plan's "be a good citizen" instruction; concurrency is purely local, against our own Postgres instance.
5. **Per-decklist error resilience**: `syncPageConcurrently` uses `Promise.allSettled` and logs+skips any individual decklist whose write fails (e.g. a hypothetical FK violation from a stale card code), rather than one bad row aborting the entire ~74k-row run. In practice, the live run had zero skips (74233/74233 succeeded).

No scope reduction: every file/route/model named in `PHASE_2_PLAN.md` was built.
